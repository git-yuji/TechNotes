# MuseにチャットだけでGitHub開発を任せてみた

## 概要

MetaのパーソナルAIエージェント「Muse」に、チャットで指示を出すだけでGitHubの開発をどこまで任せられるかを試してみた。

テスト用のリポジトリを用意し、Issueの作成、ブランチの作成、コードの変更、Pull Requestの作成、マージ、公開までを一通り進めた。人間側が行ったのは、チャットでの指示と書き込み操作の承認。

今回は、その流れと、やってみて分かったことをまとめる。テストに使ったリポジトリは非公開のため、記事内ではリンクしていない。

## 試したこと

実施したのは、次のような小さな開発タスク。

1. PRとコミットメッセージのルールを作る
2. サンプルサイトを作る
3. CSSを外部ファイルに分ける
4. Cloudflare Workersで公開する
5. AboutページやContactページを追加する
6. READMEを整える
7. デザインを刷新する
8. 不要になったContactページを削除する

GitHub上の変更は「Issueを作る → ブランチを切る → Pull Requestを作る → mainにマージする」という流れで進めた。

## 最初にルールを作った

コードを書く前に、開発ルールを`CONTRIBUTING.md`にまとめた。

- ブランチ名には`feature/`、`fix/`、`docs/`、`refactor/`、`chore/`などの接頭辞を付ける
- Pull Requestには一つの目的だけを含める
- コミットメッセージは`feat:`、`docs:`、`style:`などのConventional Commits形式にする
- PR本文は、概要・変更内容・関連Issue・確認方法・チェックリストのテンプレートに沿って書く

あわせて`.github/pull_request_template.md`も作成した。

以前書いた[AGENTS.mdの記事](/notes/agents-md-project-rules)に近い考え方で、先に進め方を決めておくと、その後の依頼がしやすくなる。

実際、この後のタスクでは、Museが自分で作ったルールに沿ってブランチ名やコミットメッセージを付けてくれた。

## サンプルサイトを作って公開する

### サイトの作成とCSSの分離

最初は、`index.html`だけの静的なサンプルサイトを作った。

Issueには、ヘッダー、紹介セクション、特徴リスト、フッターを含めることなどを記載し、Museにブランチ作成からPull Requestの作成までを任せた。PR本文には`Closes #2`が入り、マージと同時にIssueも閉じた。

次に、HTML内に書かれていたCSSを`style.css`に分けた。見た目を変えないリファクタリングなので、ブランチ名は`refactor/extract-css`になった。

タスクの内容に合わせて接頭辞が変わっていて、最初に決めたルールが使われていると感じた。

### Cloudflare Workersで公開

今回はソースのリポジトリを非公開のままにしたかったため、Cloudflare Workersを使った。

公開先を考えるときに確認したのが、GitHub Pagesの利用条件。GitHub公式ドキュメントでは、GitHub Freeは公開リポジトリが対象で、GitHub ProやTeamなどでは非公開リポジトリでも利用できると説明されている。

また、ソースが非公開でも、GitHub Pagesで作ったサイトは通常インターネット上に一般公開される。リポジトリの公開範囲と、サイトを誰が見られるかは別の話になる。

Cloudflare Workersでは、非公開リポジトリからサイトを公開できる。今回はmainブランチへマージすると自動でデプロイされ、数分でサイトに反映される設定にした。ソースは非公開、サイトは一般公開という構成だ。

## やってみて分かったこと

### ルールを先に決めると進めやすい

ブランチ名、コミットメッセージ、PRの書き方を先に決めたことで、タスクが変わっても同じ流れで進められた。その場で毎回説明するより、最初にルールを渡しておくほうがやりやすいと感じた。

### 書き込みの前に承認が入った

今回試した環境では、Issueの作成やマージなどの書き込み操作の前に、その都度承認が求められた。

AIに任せながらも、実行前に確認するタイミングがあったのは分かりやすかった。ただ、承認が入るからといって変更内容まで正しいとは限らないので、何を実行するかは自分で確認したい。

### タスクは小さく分けたほうが確認しやすい

「サイトを作って公開して」とまとめて頼むより、「ルールを作る」「サイトを作る」「CSSを分ける」と分けたことで、変更の目的と結果を追いやすかった。

問題があったときも、どのタスクで起きたかを調べやすい。今回のような試し方には、一つずつPRを確認して進める方法が合っていた。

### 判断する部分は人が見る

公開先の選択では、リポジトリを非公開にしたいのか、サイト自体を非公開にしたいのかを分けて考える必要があった。

操作をAIに任せられても、公開範囲などの判断は自分で確認したい。サービスの仕様は公式ドキュメントで確かめてから進めるのがよさそうだ。

## まとめ

Museへのチャット指示で、Issueの作成からPull Request、マージ、公開まで、一通りの開発フローを進められた。

うまく進められたのは、最初にルールを作ったことと、タスクを小さく分けたことが大きいと思う。

次は、Pull Request時にGitHub Actionsで自動チェックを動かすことや、Issueテンプレートの作成も試してみたい。
