# AGENTS.mdとは？AIコーディングエージェントへプロジェクトのルールを伝える方法

## 概要

AIコーディングエージェントへ作業を依頼するとき、毎回「回答は日本語で書く」「変更前にブランチを作る」「このコマンドでテストする」と説明するのは手間がかかる。

`AGENTS.md`は、このようなプロジェクト固有のルールや作業に必要な情報を、AIコーディングエージェントへ伝えるためのMarkdownファイル。

この記事では、Codexでの使い方を中心に、`AGENTS.md`の役割、配置場所、書いておきたい内容と注意点をまとめる。

## AGENTS.mdとは

`AGENTS.md`には、リポジトリで作業するときに守ってほしい決まりや、開発を進めるための情報を自然な文章で記述する。

たとえば、次のような内容を伝えられる。

- プロジェクトの概要と技術構成
- ファイルを変更してよい範囲
- ブランチ名やコミットメッセージの規則
- コードの書き方や命名規則
- 実行するテスト、Lint、ビルドのコマンド
- 回答やレビューコメントで使用する言語
- 実行前に確認が必要な操作

READMEが主に人へプロジェクトの使い方を説明するのに対し、`AGENTS.md`はAIコーディングエージェントが作業するときの判断基準を伝えるために使う。

ただし、すべてのAIコーディングエージェントが同じ方法で`AGENTS.md`を読み込むとは限らない。利用するツールが対応しているか、どの場所のファイルを読むかは、それぞれの公式ドキュメントで確認する必要がある。

## AGENTS.mdを置く場所

Codexでは、基本的にリポジトリのルートへ`AGENTS.md`を配置する。

```text
sample-project/
├── AGENTS.md
├── README.md
├── package.json
└── src/
```

ルートの`AGENTS.md`には、プロジェクト全体で共通するルールを書く。

特定のディレクトリだけに追加のルールが必要な場合は、そのディレクトリにも`AGENTS.md`を配置できる。

```text
sample-project/
├── AGENTS.md
├── frontend/
│   └── AGENTS.md
└── backend/
    └── AGENTS.md
```

Codexはプロジェクトのルートから現在の作業ディレクトリまでを順番に確認し、見つけた指示を組み合わせる。現在のディレクトリに近いファイルほど後から読み込まれるため、より具体的なルールで上位のルールを調整できる。

一時的に通常の指示を置き換えたい場合は、`AGENTS.override.md`も利用できる。同じディレクトリに両方がある場合、Codexは`AGENTS.override.md`を優先する。

詳しい読み込み順は、[OpenAIのAGENTS.md公式ドキュメント](https://developers.openai.com/codex/guides/agents-md)で確認できる。

## 書いておきたい内容

### 使用する言語

回答、作業報告、コードレビューなどで使用する言語を指定する。

```markdown
## 使用言語

ユーザーへの回答と作業報告は日本語で記述する。
コード、コマンド、ファイル名、エラーメッセージは、
正確性のために必要な場合は英語のままでよい。
```

「日本語を使う」だけでなく、どの文章を対象にするのか、英語のままでよいものは何かまで書くと判断しやすい。

### 作業前に行うこと

ファイルを変更する前に確認してほしいことを記載する。

```markdown
## 作業前の確認

- ファイルを変更する前に`git status -sb`を実行する
- `main`ブランチでは直接変更しない
- 作業内容に合うブランチを作成してから変更する
```

複数のエージェントや人が同じリポジトリで作業する場合、現在のブランチと未コミットの変更を先に確認するルールがあると、既存の作業へ影響する可能性を減らせる。

### テストと動作確認

変更後に実行するコマンドと、どの変更に必要なのかを書く。

```markdown
## 動作確認

- Markdownの記事を変更した場合は`npm run notes:check`を実行する
- アプリのコードを変更した場合は`npm run build`を実行する
- テストを実行できなかった場合は、理由を作業報告へ記載する
```

単に「テストする」と書くより、実際のコマンドを指定したほうが、エージェントによる判断の違いを抑えやすい。

### コミットとPull Request

コミットやPull Requestの書式だけでなく、エージェントがどこまで実行してよいかも明確にする。

```markdown
## Gitの操作

- コミットメッセージはConventional Commits形式にする
- ユーザーから依頼されない限り、コミットとpushは実行しない
- Pull Requestのタイトルと本文は日本語で記述する
```

コミット、push、デプロイなどは外部へ影響する操作になる。自動で実行してよい操作と、事前の依頼や確認が必要な操作を分けておきたい。

## 伝わりやすいルールを書くポイント

### 抽象的な表現を避ける

「適切に確認する」「きれいなコードを書く」のような表現は、人によってもAIによっても判断が変わる。

何を、いつ、どのコマンドで確認するのかを具体的に書く。

```text
変更後は適切に確認する
```

よりも、次のように書くほうが明確になる。

```text
TypeScriptを変更した場合は`npm run lint`と`npm run build`を実行する
```

### 理由や例外も短く添える

ルールだけでは判断が難しい場合は、目的や例外も書く。

```text
公開済みURLを維持するため、記事のファイル名は原則として変更しない。
```

理由が分かると、似た状況でもルールの目的に沿って判断しやすくなる。ただし、説明が長くなりすぎると重要な指示を見つけにくくなるため、作業に必要な内容へ絞る。

### 実際の構成とコマンドに合わせる

ほかのプロジェクトからコピーしたルールをそのまま使うと、存在しないコマンドやディレクトリを指定してしまうことがある。

`package.json`のスクリプト、ディレクトリ構成、現在のブランチ運用と一致しているかを確認し、プロジェクトの変更に合わせて`AGENTS.md`も更新する。

## このTech Notesで使っているルール

このTech Notesでも、リポジトリのルートに`AGENTS.md`を置いている。

主に次の内容を記載している。

- ユーザーへの回答や作業報告は日本語で書く
- 変更前にブランチと作業ツリーを確認する
- `main`ブランチではファイルを直接変更しない
- ブランチ名には変更内容に合う接頭辞を付ける
- コミットメッセージは英語の接頭辞と日本語の説明を組み合わせる
- ユーザーから依頼されない限り、コミット、push、Pull Requestの作成は行わない

これらを毎回の依頼に含めなくても、エージェントが作業を始めるときの共通ルールとして参照できる。

## ルールが読み込まれているか確認する

`AGENTS.md`を作成したら、Codexへ現在の指示を要約するように依頼して、内容が読み込まれているか確認する。

Codex CLIでは、次のようなコマンドを利用できる。

```sh
codex --ask-for-approval never "現在読み込んでいる指示を要約してください"
```

下位のディレクトリに別の`AGENTS.md`を置いた場合は、そのディレクトリから実行し、両方のルールが反映されているか確認する。

内容を変更したのに古い指示が使われているように見える場合は、Codexのセッションを開始し直す。Codexは実行またはセッションの開始時に指示を読み込むため、進行中のセッションへ変更が自動反映されるとは限らない。

## 注意点

`AGENTS.md`を書けば、すべての作業が必ず意図どおりになるわけではない。

ルール同士が矛盾していたり、長すぎて重要な内容が埋もれていたりすると、エージェントが判断に迷う可能性がある。また、テストやビルドのルールを指定しても、環境や権限の問題で実行できない場合がある。

大切な操作は作業後の報告とGitの差分を確認し、必要に応じてルールを具体的に書き直す。`AGENTS.md`は一度作って終わりではなく、実際の作業で起きた問題をもとに更新していくファイルとして扱いたい。

## まとめ

`AGENTS.md`を使うと、AIコーディングエージェントへプロジェクト固有のルールをまとめて伝えられる。

最初から多くのルールを書く必要はない。使用する言語、作業前の確認、テストコマンド、Git操作の範囲など、間違えると影響が大きい内容から記載すると始めやすい。

実際の作業で繰り返し伝えていることや、守られずに困ったことがあれば、その内容を具体的なルールとして追加していきたい。
